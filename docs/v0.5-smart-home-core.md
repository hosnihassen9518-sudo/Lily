# Lily V0.5 — Smart Home Core

V0.5 evolves the V0.4 device platform into a generic smart-home backend while preserving the current Lily RGB/audio device flow.

## New domain model

- **Home** — owned by a user and carrying its timezone.
- **Room** — belongs to a home.
- **DeviceType** — reusable hardware class such as smart light, plant sensor, smart plug, or Lily audio light.
- **DeviceTypeCapability** — capability declaration such as `power`, `brightness`, `rgb`, `temperature`, `humidity`, `soil_moisture`, `audio`, or `energy`.
- **DeviceProfile** — attaches V0.5 smart-home metadata to an existing V0.4 `Device` without changing the legacy devices table.
- **DeviceState** — latest arbitrary JSON state reported by a device.
- **DeviceTelemetry** — time-series measurements stored as metric/value rows.

## Compatibility

The V0.4 `devices` table and its RGB/audio fields are kept. This means existing V0.4 databases and the current Flutter/ESP32 behavior remain usable. New V0.5 tables are created automatically by SQLAlchemy on startup.

When a user registers, a default **My Home** is created. When an existing Lily device is claimed or activated, the backend automatically creates a DeviceProfile, assigns it to that user's first home, and associates the seeded `lily_audio_light` type.

## Seeded device types

The backend seeds these types on startup:

- `lily_audio_light`: power, brightness, rgb, audio, volume
- `smart_light`: power, brightness, rgb
- `environment_sensor`: temperature, humidity, battery
- `plant_sensor`: temperature, humidity, soil_moisture, battery
- `smart_plug`: power, energy

Admins can add more types from the API or Admin Portal.

## API additions

All routes use `/api/v1`.

### Homes and rooms

- `GET /homes`
- `POST /homes`
- `PATCH /homes/{home_id}`
- `DELETE /homes/{home_id}`
- `GET /homes/{home_id}/rooms`
- `POST /homes/{home_id}/rooms`
- `PATCH /rooms/{room_id}`
- `DELETE /rooms/{room_id}`

### Generic device model

- `GET /device-types`
- `POST /admin/device-types`
- `GET /devices/{device_id}/profile`
- `PUT /devices/{device_id}/profile`
- `GET /devices/{device_id}/state`
- `PUT /devices/{device_id}/state`
- `POST /devices/{device_id}/command`
- `POST /devices/{device_id}/telemetry`
- `GET /devices/{device_id}/telemetry?metric=temperature&limit=100`

### Admin

- `GET /admin/homes`
- Dashboard now includes homes, rooms, device types, and telemetry-point counts.

## MQTT

V0.4 topics remain supported:

```text
devices/<SERIAL>/status
devices/<SERIAL>/heartbeat
devices/<SERIAL>/state
devices/<SERIAL>/telemetry
```

The backend also listens for the V0.5 canonical form that future firmware can use:

```text
homes/<HOME_ID>/devices/<SERIAL>/status
homes/<HOME_ID>/devices/<SERIAL>/heartbeat
homes/<HOME_ID>/devices/<SERIAL>/state
homes/<HOME_ID>/devices/<SERIAL>/telemetry
```

State messages are stored as generic JSON while the legacy RGB/audio projection is still maintained for the current mobile app. Telemetry payloads can contain multiple metrics:

```json
{
  "temperature": 22.7,
  "humidity": 54,
  "battery": 81
}
```

Each metric becomes a time-series telemetry row.

## Admin Portal changes

V0.5 adds:

- Homes page
- Device Types page
- Device-type creation with capabilities
- Home/room/telemetry counters on Dashboard

## Recommended next release

V0.6 should adapt Flutter to the smart-home model with Home/Room navigation and capability-driven device widgets, then update the ESP32 firmware to advertise its type/capabilities and optionally publish through the V0.5 canonical MQTT topics.

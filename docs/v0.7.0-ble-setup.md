# Lily 0.7.0 BLE setup

Install the matching mobile APK and flash `esp32_test_light` together. The full `esp32_device` firmware still uses its earlier setup protocol.

## Flash and pair

1. Set the test-light firmware's backend/MQTT host and ports in `esp32_test_light/include/device_config.h`. They must be reachable from the selected home Wi-Fi. The backend defaults to port 6100 and MQTT to 1883. Mobile backend settings configure the phone; they do not change firmware server settings.
2. Ensure the serial/device secret exists in backend inventory with device type `test_light`. Retain your local device configuration; do not commit secrets.
3. Close the Serial Monitor and upload from the test-light folder:

   ```powershell
   pio run --target upload --upload-port COM4
   pio device monitor --port COM4 --baud 115200
   ```

4. On an unconfigured boot, Serial Monitor prints firmware `0.7.0-test-light-ble`, a Lily BLE name, and a six-digit pairing PIN. No setup Wi-Fi AP is started. If COM4 is unavailable, find the current port with `pio device list`.
5. Install mobile version `0.7.0+2`. Stop any previous running app process. Keep the phone on its normal network with access to the configured backend, sign in, open Add Device, allow Nearby devices/Bluetooth permission, and scan.
6. Select Lily and Connect. Enter the serial PIN in the operating system's pairing dialog. The first encrypted identity read triggers pairing; the dialog may appear as an Android notification.
7. Enter the exact home Wi-Fi SSID and password (2.4 GHz), choose a device name and optional home/room, then Connect and add device. ESP32 enables Wi-Fi after receiving credentials. The app shows Wi-Fi and backend activation progress over BLE.
8. After successful activation and persistent storage, BLE advertising stops; Wi-Fi/MQTT operates the LED normally. Naming/placement failures offer Retry finishing setup without resending credentials.

## Recovery

- A wrong Wi-Fi password or backend failure leaves BLE setup available; correct the input/configuration and retry. Old saved credentials are preserved on failure.
- A configured boot first tries saved Wi-Fi. If it cannot connect within 15 seconds, Wi-Fi stops and BLE recovery starts. If saved Wi-Fi connects, setup is not advertised. To reconfigure, make the saved network unavailable and restart the ESP32.
- A BLE disconnect cancels an incomplete credential message. An operation already accepted by firmware may finish even if the app closes. If uncertain, check the backend device list before restarting setup.
- After reflash or a pairing failure, forget Lily in the phone's Bluetooth settings and pair again using the current serial PIN. Bonded devices may reconnect without another PIN prompt.
- Turn Bluetooth on; on Android 11 and earlier enable Location services and grant Location permission for BLE scanning. Android 12+ uses Nearby devices permissions.
- Wi-Fi name is limited to 32 UTF-8 bytes, password to 8–63 bytes or empty for an open network. Enterprise Wi-Fi and raw 64-digit PSKs are not supported by this setup form.

## Protocol and validation

GATT service UUID is `8c9a0001-6f32-4b88-a5c1-1e1d7c6a0000`. Authenticated encryption protects identity/status reads and credential writes. Commands are version-1 newline-framed UTF-8 JSON, at most 2048 bytes, written sequentially with response and split by negotiated MTU. Status is polled every 500 ms and correlated by request ID. Notifications were omitted to avoid a read-blob race in the bundled Arduino BLE library.

Mobile tests cover UTF-8 framing, validation, token failure, ordered writes, stale status, device errors, timeout, cancellation, screen disposal, and finalization retry. Firmware and APK must compile successfully. Physical phone/ESP32 testing is still required for pairing, successful activation/LED control, wrong password, backend outage, disconnect, and saved-Wi-Fi recovery. iOS usage descriptions are included; an iOS build and hardware test require macOS/Xcode.

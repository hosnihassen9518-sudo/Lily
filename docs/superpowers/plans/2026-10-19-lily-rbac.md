# Lily v0.9.0 RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task when native execution is selected, or superpowers:subagent-driven-development if selected. Steps use checkbox syntax for tracking.

**Goal:** Ship portal-managed feature RBAC, revocable permission-snapshot sessions, delegated API credentials, and shared rate limiting as Lily 0.9.0.

**Architecture:** SQLAlchemy persists principals, roles, immutable session grants, API credentials, resource scopes, audit events and atomic rate buckets. FastAPI dependencies enforce session and object authorization; React consumes the same permission catalog. Existing device runtime signatures and hardware capability checks remain independent requirements.

**Tech Stack:** Python/FastAPI, SQLAlchemy, Alembic, SQLite/PostgreSQL, React/Vite, pytest, Vitest, Flutter regression tests.

**Spec:** docs/superpowers/specs/2026-10-19-lily-rbac-design.md

## Global Constraints

- Version backend and portal as 0.9.0.
- Fixed predefined roles: Superuser, Administrator, Operator, Read-only; custom roles remain editable.
- Resolve role grants at session issuance; validate session activity and snapshot authorization per request without rebuilding roles.
- API sessions expire after 15 minutes by default and have no refresh token.
- Rate limits: login IP 10/min, failed account 5/15min, API exchange identifier 10/min and IP 30/min, authenticated session 120/min, API principal aggregate 120/min, sensitive writes/control 30/min.
- Role/grant changes revoke affected sessions transactionally; revocation must apply across workers on the next request.
- Keep account ownership, lifecycle generations, firmware configuration and existing mobile pairing intact.
- Do not deploy or mutate live administrator assignments before live access is available.
- Push finished, verified work to GitHub as explicitly requested; use a feature branch and do not force-push.
- Never include local configs, secrets, databases, node_modules, generated assets, or unrelated lockfile changes in commits.

## Review Focus

1. Existing admin can no longer sign in after migration: exercise unique bootstrap mapping and explicit recovery failure.
2. Lower-privileged admin edits a role already assigned to another principal: enforce grant ceilings on both edits and assignments and revoke affected sessions.
3. API issuer loses permissions after key creation: exchange and existing API sessions must both lose access.
4. Multiple backend workers receive simultaneous limit or last-superuser operations: database serialization must preserve invariants.
5. Mobile/widget or signed device authentication accidentally becomes an authorization bypass: test each authentication method against protected routes and ownership boundaries.

# Lily V0.6 — Device UX & Mobile Provisioning

V0.6 keeps the V0.5 smart-home data model and focuses on the user experience and provisioning protocol.

## User experience

- My Devices remains the home/dashboard view.
- Devices are grouped by Home and Room.
- Device cards show live online/offline status and provide three primary actions: Off, Play/Stop and More.
- Tapping the card or More opens the device detail page.
- Detail controls are capability-aware (power/light/brightness/RGB/audio/volume).
- Users can create, rename and delete homes and rooms, and move devices between rooms.
- Flutter Web uses a side NavigationRail; Android/iOS use bottom navigation.
- Adding/provisioning devices is mobile-only.
- Authentication validation errors are shown inline (invalid email, password shorter than 8 characters, server validation failures).

## Provisioning protocol

The ESP32 setup AP is open/passwordless and advertises its type in the SSID, for example:

`LILY-AUDIO-LIGHT-000001`

The mobile app filters discovered Wi-Fi networks to names beginning with `LILY-` and validates identity using `GET /info`.

`GET /info` returns serial, device type key/name, firmware and capabilities.

`GET /networks` asks the ESP32 to scan nearby home Wi-Fi networks so the user can select an SSID in the app.

`POST /provision` now tests Wi-Fi credentials before reporting success. If association fails, the ESP32 returns HTTP 422 with a readable error and keeps its Lily setup AP active. Credentials are saved only after Wi-Fi and backend activation succeed.

## Device-type registration

Firmware sends `device_type_key` to `/api/v1/devices/activate`. The backend maps the claimed device to the matching V0.5 DeviceType so future device types can advertise different capabilities without rebuilding the dashboard.
